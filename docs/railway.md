# Шедулер на Railway Cron Jobs (фаза C)

Переезд кронов с GitHub Actions: код и сырьё уезжают в приватный репо БЕЗ
Actions, расписания встают на Railway Cron Jobs (контейнер node+git), наружу
публикуется только витрина — в отдельный публичный serve-репо нейтральными
коммитами «data update» по deploy key. Railway-аккаунта ещё нет: всё в этом
документе проверяемо локально (§8), а места, где поведение платформы надо
подтвердить на живом аккаунте, помечены явно.

Артефакты: `deploy/railway/Dockerfile`, `deploy/railway/entrypoint.sh`,
`.dockerignore` (белый список входа билда). Запуск — по конвенции оркестратора:
`tsx src/orchestrator.ts <группа> [--run | --push]` (без флагов — только
печать плана, `--run` — прогон без git, `--push` — боевой); группы:
`snapshot`, `snapshot-daily`, `f1live`, `fia`, `weclive`, `tracks`.

> **Несделанное, без которого чеклист §2 не завершать:** пуш витрины в
> serve-репо оркестратор ПОКА НЕ ДЕЛАЕТ — `--push` пушит только в origin
> (приватный репо), см. шапку src/orchestrator.ts. Сборка витрины уже есть
> отдельным скриптом (`tsx src/exportserve.ts --dest <кат> [--write]`,
> состав строго по src/lib/databoundary.ts); осталось вшить в оркестратор
> шаг «exportserve → коммит „data update“ → push по `SERVE_REPO_URL`».
> Пока шага нет, кроны наполняют приват, а публичный serve-репо не
> обновляется — приложение таким переездом ослепло бы.

## 0. Устройство контейнера: почему в образе нет кода

Кроны пушат данные в приватный репо десятки раз в сутки. Образ с кодом внутри
пришлось бы пересобирать на каждый такой пуш — либо смириться, что крон бежит
на отставшем коде. Поэтому:

- образ = node:20-slim + git + запечённые node_modules + entrypoint; ни кода,
  ни data/ в нём нет;
- на каждом прогоне entrypoint сам делает `git clone --depth 1` приватного
  репо (по deploy key) и запускает оркестратор из свежего клона;
- деплой кода = обычный `git push` в приватный репо: следующий тик крона
  подхватит свежий main, ни пересборки, ни redeploy не нужно;
- пересборка образа нужна ровно в двух случаях: сменились зависимости
  (package-lock.json) или сам entrypoint;
- `npm ci` на каждый 15-минутный прогон не платится (замена setup-node +
  npm-кэша Actions): node_modules запечены слоем образа, entrypoint симлинкует
  их в клон, пока package-lock.json клона байт-в-байт совпадает с запечённым.
  Разошлись — ставит на месте (прогон корректный, но медленный) и пишет в лог
  требование пересобрать образ;
- `.dockerignore` собран белым списком из четырёх файлов — вход билда не зависит
  ни от кода, ни от данных, поэтому даже случайная авто-пересборка на пуш
  данных упрётся в кэш слоёв;
- свежий клон на прогон дополнительно закрывает гонки: у сервисов нет общего
  чекаута, который в Actions приходилось делить concurrency-группой (§5).

## 1. Крон-матрица: GH Actions → Railway Cron Jobs

Все расписания — UTC (у Railway cron-выражения тоже в UTC, переносимы как
есть). Один образ на всех, сервисы различаются расписанием и start command.

| GH Actions | было | Railway-сервис | cron (UTC) | start command |
|---|---|---|---|---|
| snapshot.yml, часовой | `17 * * * *` | `snapshot` | `17 0-2,4-23 * * *` | `/entrypoint.sh snapshot --push` |
| snapshot.yml, суточный (сезон N+1) | `37 3 * * *` | `snapshot-daily` | `17 3 * * *` | `/entrypoint.sh snapshot-daily --push` |
| f1live.yml | `*/15 * * * 5,6,0` | `f1live` | `7,22,37,52 * * * 5,6,0` | `/entrypoint.sh f1live --push` |
| fia.yml | `*/15 * * * 5,6,0` | `fia` | `*/15 * * * 5,6,0` | `/entrypoint.sh fia --push` |
| weclive.yml | `*/15 * * * *` | `weclive` | `*/15 * * * *` | `/entrypoint.sh weclive --push` |
| tracks.yml | `0 4 * * 1` | `tracks` | `0 4 * * 1` | `/entrypoint.sh tracks --push` |

ci.yml — не крон и на Railway не переезжает, см. §6.

Почему матрица не один-в-один:

- **snapshot-daily встаёт В слот часового (03:17), а не рядом с ним.** В GH
  суточный прогон `37 3` был полным snapshot-прогоном + шаг nextseason, и от
  часового `17 3` его отделяла concurrency-группа (сериализация). На Railway
  межсервисной сериализации нет: два полных прогона в 03:17 и 03:37 реально
  пересеклись бы и толкались rebase-конфликтами на одних файлах. Поэтому
  часовой в 03:xx не бежит вовсе, а суточный занимает его минуту. Итог: 24
  полных прогона в сутки против 25 в GH (там суточный `37 3` был ДОПОЛНИТЕЛЬНЫМ
  полным прогоном рядом с часовым `17 3`) — минус один прогон в 03:xx, цена
  отказа от межсервисной сериализации; один из 24 — с довеском SEASON=N+1.
  Контракт для оркестратора: группа `snapshot-daily` = ВЕСЬ snapshot-набор +
  nextseason, а не только четыре продьюсера с SEASON=N+1 — иначе из суток
  выпадает один полный прогон.
- **f1live сдвинут на `7,22,37,52`.** В GH он делил группу `snapshot` и просто
  вставал в очередь за часовым прогоном; на Railway они бежали бы одновременно,
  а оба пишут data/f1/openf1 (и highlights/events) — это уже не push-гонка, а
  содержательный rebase-конфликт двух разных версий одного файла. Сдвиг даёт
  часовому snapshot 5 минут форы на слоте :22 и сохраняет 15-минутный каденс.
  Если замер первой недели покажет, что snapshot регулярно живёт дольше 5
  минут, — двигать дальше или включать git-lock (§5).
- **fia и weclive — без изменений.** У них и в GH были СВОИ группы (иначе
  15-минутные прогоны молча дропались в очереди за часовым — ровно в
  уик-энд); пишут непересекающиеся пути (data/f1/fia, data/wec), параллельность
  со snapshot безопасна, push-гонку разруливает rebase-retry оркестратора.
- **tracks — без изменений.** Группу `snapshot` он делил только из-за общего
  чекаута в Actions; при клоне-на-прогон пересечения файлов со snapshot нет
  (пишет только data/tracks), а до 04:17 его единственный батч-запрос успевает
  с запасом.
- **weclive — мерило успеха переезда.** Воркфлоу существует потому, что GH
  ронял расписания (27.08.2026 — разрывы 4.6 и 10.25 ч). Если каденс `*/15` на
  Railway не окажется честнее, переезд шедулера теряет половину смысла —
  проверить по data/health.json и таймстемпам коммитов за первую неделю.

## 2. Чеклист владельца

1. Завести аккаунт Railway, план Hobby. Биллинг поминутный по ресурсам
   работающего контейнера — короткоживущие крон-прогоны дёшевы, но через
   неделю сверить фактический usage с ожиданиями.
2. Создать проект (одного окружения достаточно).
3. Источник образа — два варианта:
   - подключить приватный репо к Railway и указать сервисам Dockerfile
     `deploy/railway/Dockerfile` (Railway соберёт образ сам);
   - если давать интеграции Railway доступ к приватному репо не хочется —
     собирать образ локально (`docker build -f deploy/railway/Dockerfile .`)
     и деплоить из Docker-реестра; тогда единственный доступ к коду у
     платформы — deploy key из переменных.
4. Создать шесть сервисов по матрице §1. В настройках каждого:
   - cron-расписание из матрицы (проверить, что Railway трактует его в UTC);
   - start command из матрицы (первый прогон — временно без `--push`, см. п. 7);
   - restart policy «не перезапускать при падении»: повтор упавшего прогона —
     дело следующего тика, а автоперезапуск в цикле жёг бы деньги и смазывал
     алертинг;
   - авто-деплой из репо выключить или ограничить watch paths входами билда
     (`deploy/railway/**`, `package.json`, `package-lock.json`) — иначе каждый
     пуш данных будет дёргать пересборку (пусть и кэшированную).
5. Прописать переменные (§3): общие — на уровне проекта (shared), в сервисы —
   ссылками. GROUP задавать не нужно — группа передаётся аргументом start
   command.
6. Сгенерировать и прописать deploy keys (§3).
7. Ручной прогон каждого сервиса с `--run` вместо `--push` (без флагов
   оркестратор печатает план и выходит — лог был бы ложно-зелёным), сверить:
   клон прошёл, node_modules подцепились симлинком, оркестратор отработал
   группу. Затем вернуть `--push` и проверить, что в serve-репо появился
   коммит «data update» (пока serve-шаг не вшит — см. врез в начале дока,
   этот пункт его и ловит).
8. Настроить алертинг (§4) — до этого падения кронов молчат.
9. Неделя наблюдения: каденс коммитов и data/health.json против истории GH.

## 3. Секреты и переменные

| Переменная | Что это | Пример |
|---|---|---|
| `PRIVATE_REPO` | owner/name приватного репо (код + сырьё) | `gradora/overlap-data-private` |
| `PRIVATE_REPO_SSH_KEY` | приватная половина deploy key приватного репо, **RW** | `-----BEGIN OPENSSH PRIVATE KEY-----…` |
| `SERVE_REPO` | owner/name публичного serve-репо (витрина) | `gradora/overlap-serve` |
| `SERVE_REPO_SSH_KEY` | приватная половина deploy key serve-репо, **RW** | — |
| `GIT_USER_NAME` / `GIT_USER_EMAIL` | identity коммитов | `overlap-bot` / `overlap-bot@users.noreply.github.com` |
| `CLONE_BRANCH` | ветка клона, по умолчанию `main` | — |
| `CLONE_URL` | оверрайд источника клона — только для локального dry-run | `file:///work/host` |
| `GROUP` | группа, если не передана аргументом | `snapshot` |

Генерация ключей (по одному на репо — GitHub не разрешает один deploy key на
два репозитория, поэтому entrypoint разводит их через два ssh-алиаса одного
github.com):

```sh
ssh-keygen -t ed25519 -N "" -C railway-overlap-private -f overlap_private_deploy
ssh-keygen -t ed25519 -N "" -C railway-overlap-serve   -f overlap_serve_deploy
```

Публичные половины — в Deploy keys соответствующих репо на GitHub с галкой
«Allow write access»; приватные — целиком (многострочно) в переменные Railway.

Почему оба RW:

- приватный: кроны коммитят собранные данные обратно в приватный репо — data/
  живёт там же, где код;
- serve: пуш витрины нейтральными коммитами «data update» — шаг оркестратора,
  который ЕЩЁ НЕ ВШИТ (см. врез в начале дока); ключ заводится сразу, чтобы
  чеклист не возвращался к секретам.

Гигиена: deploy key ограничен одним репозиторием — это весь blast radius при
утечке (ревок — в настройках репо). Entrypoint убирает ключи из окружения до
запуска оркестратора и не включает трассировку шелла, чтобы ключи не утекали
в логи платформы.

## 4. Алертинг: замена писем GitHub

Что было: гейты (упавшие продьюсеры, свежесть) валят job → GitHub сам шлёт
письмо владельцу о падении scheduled workflow. Бесплатный канал без настройки —
и единственный.

Что на Railway: ненулевой exit контейнера пометит прогон упавшим в дашборде,
но письмо само по себе не прилетит — без явной настройки гейты становятся
декоративными. Замена, два слоя:

1. **Уведомления Railway**: в настройках проекта есть вебхуки на события
   деплоя/падения (доставка в Slack/Discord/произвольный HTTP-эндпоинт). Как
   именно завершение крон-прогона с ненулевым кодом мапится на эти события —
   проверить на живом аккаунте при настройке (п. 8 чеклиста): это самая зыбкая
   часть переезда.
2. **Notify-шаг в оркестраторе** — рекомендуемый основной канал: после гейтов,
   при FAILED/STALE, POST в вебхук владельца (Telegram-бот / ntfy / почтовый
   мост — что угодно с URL в переменной окружения). Не зависит от платформы
   вообще и переживёт следующий переезд.

Что теряем против GitHub и чем компенсируем:

- annotations `::error::`/`::warning::` в UI → обычный stderr в логах Railway
  (гейты и так дублируют всё текстом);
- история прогонов Actions → логи Railway со своим ретеншном; выводы гейтов,
  которые нужны надолго, и так коммитятся в data/health.json;
- письма из коробки → слои 1–2 выше, настраиваются руками.

## 5. Отличия семантики: concurrency и ручные запуски

**Concurrency-группы GitHub** давали два свойства: (а) сериализацию писателей
одних файлов (группа `snapshot` = snapshot + f1live + tracks); (б) «максимум
один pending, лишние тики молча дропаются». На Railway:

- (б) есть per-service из коробки: новый прогон крон-сервиса не стартует, пока
  предыдущий прогон того же сервиса ещё жив — лишний тик пропускается, очередь
  не копится (поведение платформы, подтвердить при настройке);
- (а) между сервисами не существует — но и нужна она в прежнем объёме не была:
  сериализация защищала ОБЩИЙ чекаут Actions, а здесь каждый прогон работает в
  собственном свежем клоне. Пересечение осталось только в точке push;
- push-гонку (два сервиса пушат в один репо одновременно) разруливает
  rebase-retry в оркестраторе — прямое наследие composite action commit-push
  (5 попыток `pull --rebase` + push);
- остаточный риск — содержательный rebase-конфликт: два прогона закоммитили
  РАЗНЫЕ версии одного файла. Единственная такая пара — snapshot × f1live
  (оба пишут data/f1/openf1 и производные), закрыта разносом расписаний в §1.
  Если конфликтные падения всё же станут регулярными — git-lock
  веткой-семафором в оркестраторе. Вариант с flock на общем volume не годится:
  volume Railway крепится к одному сервису, общего файлового пространства у
  крон-сервисов нет;
- независимость fia и weclive от snapshot (в GH — отдельные группы) получается
  сама собой: отдельные сервисы друг о друге не знают и в очередь друг за
  другом не встают.

**workflow_dispatch** (ручной запуск, все 6 воркфлоу):

- локально: `tsx src/orchestrator.ts <группа> --run` — прогон без git (без
  флагов печатается только план); с `--push` — боевой запуск с локальной
  машины (нужны ключи);
- в облаке: redeploy сервиса в дашборде Railway даёт внеочередной прогон
  контейнера вне расписания;
- `railway run` из CLI выполняет команду ЛОКАЛЬНО с переменными окружения
  сервиса — удобно для отладки контракта env (клон, ключи), но облачным
  прогоном не является.

**`github.event.schedule`** (часовой vs суточный внутри одного воркфлоу) →
два отдельных сервиса с разными группами (`snapshot` / `snapshot-daily`).
Ручной аналог `inputs.next_season` — просто запустить группу `snapshot-daily`.

**Каденс**: гарантий «минута в минуту» Railway не обещает; мотивация переезда —
не идеальность, а честность против GH, который терял часы. Замер — §1,
последний пункт.

## 6. Что НЕ переезжает

- **fomstatic и f1pitawards** — ручные и остаются ручными локальными запусками
  владельца: источники (livetiming.formula1.com, formula1.com) режут облачных
  раннеров, у Railway egress того же класса, и решение «не скрейпить FOM из
  крона» — осознанное. Реестр src/lib/producers.ts так их и учитывает
  (`manual`), гейт свежести их не считает.
- **ci.yml**: сторож «возврат кухни в публичный репо через data-коммит» теряет
  и площадку (Actions), и предмет (репо приватный — класс риска другой).
  Typecheck + тесты гонять локально pre-push (git-хук); опционально — седьмой
  крон-сервис `tests` раз в сутки (`npm run typecheck && npm test` вместо
  оркестратора) как страховка от забытого хука. В матрицу §1 не включён —
  решение за владельцем.
- **commit-push** (composite action) переезжает не сюда, а в оркестратор:
  rebase-retry остаётся, message-prefix с именем продьюсера для serve-репо
  заменяется нейтральным «data update».
- **src/workflows.test.ts** («каждый продьюсер вписан в канал с расписанием»)
  обязан быть перенацелен с парсинга .github/workflows/*.yml на конфиг групп
  оркестратора — иначе сторож класса «забытый продьюсер» (инцидент f1teams,
  17 суток) умрёт молча. Это зона оркестратора; отсюда — требование: имена
  групп = имена Railway-сервисов = поле `workflow` реестра
  src/lib/producers.ts, одно пространство имён.

## 7. Контракт контейнер → оркестратор

Оркестратор пишется параллельно; контейнер гарантирует ему:

- cwd = корень свежего клона приватного репо (`/work/repo`), ветка
  `CLONE_BRANCH` (по умолчанию main), depth 1;
- argv: `<группа> [--push и прочие флаги]` — как передали контейнеру;
- `origin` клона — приватный репо, push в него доступен по уже настроенному
  ключу (data-коммиты);
- env `SERVE_REPO_URL` — готовый ssh-URL витрины (через алиас `github-serve`);
  контракт для будущего serve-шага при `--push` (сейчас оркестратор его не
  читает — см. врез в начале дока); ssh-ключи и алиасы — забота контейнера;
- git identity настроен глобально;
- exit-код оркестратора = вердикт прогона для Railway: гейты обязаны выходить
  ненулём (замена «гейт валит job → письмо»), падение продьюсеров не должно
  мешать health/commit/push до гейтов — как в snapshot.yml.

## 8. Локальный dry-run (без Railway-аккаунта)

Без Docker — оркестратор с `--run` (без флагов печатается только план):

```sh
npx tsx src/orchestrator.ts snapshot --run
```

С Docker — полный прогон контейнера, клон из примонтированного локального
репо вместо GitHub, без ключей и без пуша:

```sh
docker build -f deploy/railway/Dockerfile -t overlap-cron .
docker run --rm -v "$PWD:/work/host:ro" -e CLONE_URL=file:///work/host \
  overlap-cron snapshot --run
```

Оговорки: `file://` обязателен (клон по голому пути игнорирует `--depth`);
клонится только закоммиченное — незакоммиченные правки в прогон не попадут;
node_modules хоста не участвуют (в контейнере — запечённые linux-бинари, а не
macOS).

Репетиция `--push` целиком — пуши в локальные bare-репо: read-only клон
хост-репо тут не годится (оркестратор пушит данные в origin), поэтому origin —
одноразовая bare-копия рабочего репо. Оговорка: пока serve-шаг не вшит
(врез в начале дока), наполнится только private.git, а /tmp/serve.git
останется пустым — это ожидаемо и как раз маркер несделанного:

```sh
git clone --bare . /tmp/private.git
git init --bare /tmp/serve.git
docker run --rm \
  -v /tmp/private.git:/work/private.git -v /tmp/serve.git:/work/serve.git \
  -e CLONE_URL=file:///work/private.git -e SERVE_REPO_URL=file:///work/serve.git \
  overlap-cron snapshot --push
```

Ssh-алиасы при готовых file://-URL не нужны — entrypoint настраивает их,
только когда заданы ключи.
