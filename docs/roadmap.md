# Overlap — план завершения бэка (снимок 10.09.2026)

Цель трека: ПОЛНОСТЬЮ закрыть работу с бэком — поток данных, хранение,
оркестрацию и переезд на Railway. Продуктовые фичи и релизные ритуалы —
в бэклоге внизу и на трек не влияют (TestFlight из плана исключён:
он нужен только владельцу и ничего не гейтит).

## Definition of Done трека

- Клиент читает ТОЛЬКО наше зеркало + ассеты; из чужих API остаётся
  один осознанный инвариант — живое окно Al Kamel у IMSA.
- В витрине нет ни имён источников, ни чужих идентификаторов (D-финал).
- Код + сырьё — в приватном репо; публичный serve-репо с нейтральным
  именем и чистой историей несёт только витрину; кроны — на Railway с
  работающим алертингом; GH Actions выключены; старые SHA публичного
  репо отдают 404 (уходит и хвост «сырьё в git-истории»).
- Лайв-поток определён: записи фида разобраны, форма лайв-заготовки
  зафиксирована, рекордер — штатный инструмент.
- Операционка задокументирована: ритуалы, бюджеты свежести, процедуры
  бампов (уже в docs/f1-kitchen-plan.md и railway.md).

## Этапы (порядок = рекомендуемый)

### 1. D-лайт — витрина без имён источников (сейчас, ~день)
sourceIds.jolpica → свои поля (confirmed/round); sourceIds.fiawec —
выпилить (проверить остаточное клиентское чтение); `f1-meeting-*` →
наши слаги (миграция id файлов витрины — forecast/weather/events);
openf1.meetingKey → нейтральное топ-поле (число остаётся до D-финала).
Итог: sourceleak-сторож без исключений на имена источников. Бэк+клиент
одним окном, дисциплина эталонов как у конвертации.

### 2. Разбор записи Монцы → форма лайв-заготовки (сейчас, параллельно 1)
Выжимки: stationary-питы (сверка с DHL/openf1 — возможно, фид чинит
дыру stop_duration лучше обоих), стинты, полный рейс-контрол.
Решения на выходе: форма «заготовки лайва» в data/, писать ли следующие
гонки (рекордер готов), судьба сырья записи в привате.

### 3. Обкатка Мадрида (11–13.09, пассивно) + пост-этапные ритуалы
Первый живой уик-энд f1live на фактах: смотреть каденс, предполёт,
pit-heal. После этапа: `npm run f1pitawards`, preferredTire Мадрида,
brands.json при изменениях.

### 4. Витрина архива 2023–24 — смерть каскада openf1 (крупный, ~дни)
Хвост фазы 6: календарь v2 и файлы событий для сезонов 2023–2024,
чтобы клиентский каскад (meetings/sessions/drivers/session_result/
stints/race_control из f1/openf1) умер целиком. Разведка → дизайн →
конвертация по образцу сделанных этапов. Это ЕДИНСТВЕННОЕ, что держит
clientReads у заготовки f1/openf1 и числовые ключи openf1 в контракте.

### 5. Клиентский срез 0.6.7 (после Мадрида — цикл обкатки есть)
Снять остатки: jolpica-ветки промаха current*, цепочки OpenF1 экрана
события (после этапа 4 они мертвы по построению), прямой Open-Meteo +
словарь координат + makeTypical, каскад архива → витрина 2023–24.
Сюда же: решение по глубокому архиву погоды (WEC 2011+ — бэкфилл или
честное отсутствие страницы; нужна разведка событийных id).
Оговорка N+1: фолбэк loadSessions для событий без файла живёт до
1 января — единственный осознанный остаток.

### 6. D-финал — свои числовые id (после 4+5, ~день)
session_key/meetingKey в витрине → наши id; f1/openf1 → clientReads
false (чистая заготовка); сторожа ужесточаются; SnapshotMirror-каскад
и парный slug-тест уходят.

### 7. Фаза C — сплит и Railway (по готовности владельца; механика ждёт)
🔑 От владельца: аккаунт Railway + Hobby; ИМЯ публичного serve-репо;
два deploy-ключа (команды в railway.md §3); опционально Docker Desktop
для локальной репетиции образа.
День Х (пол-дня, по чеклисту railway.md §2): код+сырьё+доки в приват;
пересоздание публичного репо (критерий приёмки — 404 по старым SHA);
шесть крон-сервисов по матрице §1; переменные и вебхук нотификатора;
первый прогон каждого сервиса с --run, затем --push; проверка «в
serve-репо появился data update». Умирают: moments.json,
refs/matching.json, health в публичном, workflows.test (покрытие
остаётся на orchestrator.test), ci.yml.
